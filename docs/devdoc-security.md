# DevDoc AI Security Controls

DevDoc sends a bounded instruction and JSON context to its configured AI provider. The vendor-neutral `AIProvider` validates requests before provider code runs. The OpenAI adapter uses the existing Responses API architecture with response storage disabled, fixed sanitized exception messages, structured output validation, and configurable request and response byte limits (1,000,000 bytes by default).

## Outbound data checks

The secret scanner detects and redacts common AWS and GitHub keys, Stripe and Slack token formats, sensitive assignments including client secrets and session tokens, password assignments, API and OAuth token assignments, bearer tokens, JWT-like three-part values, database connection URLs, credentials embedded in HTTP(S) URLs, and supported PEM private-key blocks, including encrypted private keys. Incomplete supported private-key blocks are treated as sensitive through the end of the supplied text. Context building omits files containing detected private-key material and applies per-file and aggregate size limits.

The provider gate scans the complete instruction and nested JSON context before a provider request. Values that cannot be serialized as JSON are rejected; their custom string representations are not invoked. Document-type labels are constrained in length and character/word shape before they are included in the generation instruction. API exception details are mapped to fixed messages. Unrecognized or malformed response metadata is omitted, and oversized response text is rejected before JSON parsing. The optional OpenAI SDK requirement is pinned to a specific official wheel and SHA-256 digest; its transitive dependencies are not yet represented in a cross-platform hash lockfile.

## Generated output checks

Before the documentation reviewer sees a generated draft, `OutputValidator` treats it as untrusted output and checks it for credentials, selected high-risk command forms, common prompt-injection or credential-disclosure phrases, malformed structure, required sections, and headings associated with a different requested document type. Required headings are counted only outside fenced code, HTML comments, and recognized raw HTML blocks. CommonMark-style raw HTML blocks, including block tags and standalone closing tags, remain active through the next blank line; raw-text elements such as `script`, `pre`, `style`, and `textarea` remain active through their closing tag. Unclosed fences, comments, or tracked HTML blocks make the output invalid. Command checks recognize common nested list and blockquote prefixes, direct command lines, selected `run` or `execute` instructions followed by a selected high-risk command, and shell backslash-newline continuations. Clearly negated forms such as “do not run” and “never execute” are treated as safety advice, while supported positive execution instructions are blocked. The validator reuses `SecretScanner`; detected credentials are redacted in the returned draft and reported as validation issues. A draft with any output-validation issue is marked ineligible for the normal human review path. The CLI marks blocked output as diagnostic only, explains validation failures, and exits unsuccessfully. Valid drafts continue through the existing documentation reviewer, and human approval remains mandatory.

Generated commands are never executed. Output validation is separate from the request/context provider gate and from any execution controls. DevDoc does not automatically execute, save, approve, or publish generated documentation.

## Limitations

Secret detection is pattern based. It cannot identify every credential format, encoded or split secrets, arbitrary private-key formats without supported PEM markers, or secrets hidden in binary/unsupported files. The added provider-specific and sensitive-assignment patterns reduce known gaps but do not make detection complete. JWT-like detection is heuristic and can miss short or unusually encoded tokens or flag token-shaped non-credentials. The HTTP URL matcher covers common user/password authority syntax; it does not decode or inspect every URL encoding scheme. Command checks remain pattern based: they cover selected command forms, common Markdown prefixes, and backslash-newline shell continuations, but can miss unfamiliar, aliased, encoded, quoted, or otherwise reformatted commands. They do not parse or evaluate shell syntax and must not be treated as proof that an accepted command is safe. Positive prose detection recognizes bounded `run`/`execute` phrases, including colon-delimited instructions with intervening words; negation handling recognizes a bounded set of explicit forms, so complex wording or quoted examples may still be blocked or missed. Prompt-injection phrase checks are also heuristic: they block selected textual patterns but cannot establish that a model followed the intended trust boundary or prevent indirect prompt injection. The heading scanner is a conservative line-oriented parser for common fences, HTML comments, raw-text elements, and CommonMark-style raw HTML block boundaries, plus declarations, processing instructions, and CDATA sections. It is not a complete CommonMark or HTML parser; unusual nesting, malformed markup, or renderer-specific parsing may be rejected or interpreted differently. Heading-based document-type checks can miss semantic drift that does not alter headings. Generated commands are not executed, and human review remains necessary.

The configured byte limits bound serialized request instruction/context and returned response text, not total SDK memory, transport overhead, provider-side processing, or all possible provider metadata. Defaults and sanitization have local unit-test coverage; no external API request or live credential is used by these tests. These controls are not a guarantee that all sensitive information will be detected.
